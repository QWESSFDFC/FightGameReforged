## 决定

- 否决“代码生成表定义”的 A/B 两条路；改选**反射混血**：键清单交给反射/手写表，
  顺序、子块、重算、别名留在手写编排里。
- 项目第 0 条要求“不重复分析已否决方案”；以后有人再提议这条路线，先看本文。

## 为什么否决

- **A 路永久出局**：行为/公式不可生成；继承链无法用表表达；生成物缺席会让全项目不编译；
  没有可枚举的内容表。
- **B 路只剩方法论**：表列写 Java 符号、javac 兜底，确实能查错；但“表只多住一行”的收益
  抵不过多一步手工构建、自维护生成器、二进制产物 diff。

## 当时的三口径（决策依据）

| 路线 | 改一处要做什么 |
|---|---|
| 现状（手写表） | 改 1 个文件 1 行 |
| 纯反射 | 改 0 处（但顺序/子块/重算不可控） |
| 本方案（代码生成） | 改 1 行表 + 跑 1 次生成 + 提交 1 个产物 diff |

## 仍然有效的约束

- `/data` 键名不改；运行期不读 xlsx；不切换/不删除反射；不做热重载；不生成属性类。
- 失败模式互补：表默认关闭（漏行会静默）、反射默认开放（忘挡会多键），所以保留两边。
- 零依赖优先；不押新依赖（离线/换机/镜像/公开仓库）。
- 推翻门槛：必须给出比“反射 0 处”更省的数字，否则不重开。

## 已排除的子选项

- 只生成键声明、不生成表；`DataKeys` 不生成；不做成 gradle task；不生成属性类。
- 生成器行数、文件数、会话环境快照不再维护；需要细节看归档稿。
