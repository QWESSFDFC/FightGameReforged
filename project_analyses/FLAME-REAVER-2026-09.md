## 2. 官方机制（权威数据，勿凭记忆改）

来源：官方 wiki 内容 4982 / BWIKI 源码（原文明写「物理属性」，本项目一律映射为**火属性**）。

### 2.1 BOSS 基础

- 名称：至黑之剑，盗火行者（别称 黑厄 / 卡厄斯兰那 / 盗罐行者 / 刽子手）
- 种类：首领（剧情 BOSS），出现地点：主线-翁法罗斯
- 速度 132~174，**韧性 240**（本项目不做），召唤物：**残破容器**
- **状态抵抗：冻结抵抗、纠缠抵抗、禁锢抵抗**
- 弱点：量子、雷、冰；抗性：物 20% / 火 20% / 风 20% / 虚数 20%，冰雷量子 0%
- 阶段数 **2**

### 2.4 召唤物：残破容器

- 种类：普通（**召唤物**）
- **为我设奠**：处于**【镣锁】状态**下受到致命攻击时，若盗火行者的【灾难之力】层数不为 0，
  **立即被其重新召唤并回到【镣锁】状态**，但会让盗火行者**失去 1 层灾难之力和一定比例生命值**。
  盗火行者施放【莫因舍弃而哭泣】时，它会被**吸收**，回复转化为【苦痛缠绕】的生命值。
- **为我祷咏**：**抵抗控制类负面状态**。当盗火行者**再次**施放【亡死的黑云】或【将尽的命数】时，
  若自身**曾被该攻击召唤且处于【共祭】状态**，则**与盗火行者一同发起攻击**；
  随后被吸收，回复转化为【苦痛缠绕】的生命值，并使其获得【灾难之力】。
- **共祭 · 将尽的命数**：对**我方全体**造成少量伤害，被击中目标降低生命值的一部分转化为【侵蚀】。
- **共祭 · 亡死的黑云**：对指定我方单体**及其相邻目标**造成少量伤害。

### 2.5 从数据里读出来的设计意图（实现时必须保住）

1. **苦痛缠绕是"代价-回收"账本**
   召唤时按**消耗的生命值**记账，吸收时按【苦痛缠绕】**回血**。
   玩家杀掉容器 → 这笔账永远收不回来 → 这是杀召唤物的核心收益。
2. **来源绑定**
   能被吸收 / 能一同攻击的容器，必须是「**曾被这次攻击召唤**」且处于【共祭】的那批。
   不是无差别吸收场上所有容器 —— 这条决定了「相混的道途（上共祭）」的价值。
3. **减伤是层数制，且与容器数量挂钩**
   【永别的决绝】给若干层减伤，**每死一个残破容器掉 1 层** → 玩家清容器 = 削 BOSS 减伤。
4. **灾难之力双向**
   吸收容器 **+1**；阶段二【为我设奠】用 **−1** 换容器复活。大招**消耗全部**换伤害。
5. **侵蚀是持续压力**
   由【将尽的命数】（BOSS）和【共祭·将尽的命数】（容器）挂上，
   效果是「被击中目标**降低生命值的一部分**转化为侵蚀」→ 侵蚀与"损失的生命值"挂钩。
6. **两大招的区别**
   阶段一「却是必要的苦难」= 先按层数打多段，**再补一发全体**；
   阶段二「莫因舍弃而哭泣」= 先打全体，**再按层数补多段**（顺序相反）。

## 3. 对本项目的映射

### 3.1 属性与目标

- 所有「物理属性伤害」→ **火属性**；
- 「主目标及其相邻目标」→ **目标数 3**（用技能自带的 `aims` 字段，`CommonAttack(0, 1, 0, 2)` 就是范例）；
- 抗性表：本项目按需求填（默认给火抗，因为自己就是火属性）。

### 3.2 形态一（阶段一）：苦痛缠绕闭环 + 减伤层数

| 官方 | 本项目做法 |
|---|---|
| 亡死的黑云（扩散） | 3 目标火伤 + **召唤 1 个残破容器**，代价 = BOSS 最大生命的 X%，记入苦痛缠绕 |
| 将尽的命数（群攻） | 全体火伤 + 挂【侵蚀】+ **召唤 1 个残破容器**（同上） |
| 相混的道途（强化） | 让场上容器进入【共祭】状态（数个行动内可用【幽冥的悼念】） |
| 幽冥的悼念 | 与【共祭】容器一同出手（容器各自放【共祭·亡死的黑云】/【共祭·将尽的命数】），然后**吸收**：按苦痛缠绕回血 + 获得灾难之力 |
| 却是必要的苦难（大招） | 消耗全部灾难之力 → 全体多段（段数 = 层数）→ 追加一次全体伤害 |
| 永别的决绝（天赋） | BOSS 身上一个减伤**层数**（每层 X%，乘算来源键）；**每死 1 个残破容器掉 1 层** |
| 分离的哀痛（天赋） | 上面「召唤 + 记账 + 来源绑定 + 吸收回血充能」这套逻辑的载体 |

### 3.3 形态二（阶段二）：按"融合"改写

- 触发条件待定（建议血量 50%）；
- **替代「退居幕后」**：BOSS 获得**高额免伤**（独立减伤来源键，不可清除），持续到条件结束；
- 加入【沉默的悲叹】→ 蓄力 → 【莫因舍弃而哭泣】的**预告-兑现**节奏；
- 加入【迷失的共祭】/【镣锁】：**灾难之力 ≥1 时，镣锁容器被杀会被消耗 1 层灾难之力复活**；
- **完整容器**（末日幻影 3.4 融合）：击杀 → **击杀者获得额外回合 + 增伤 buff**；
  没击杀 → BOSS 吸收，**额外充能**。它是"奖励线"，与残破容器的"泄压阀"形成取舍。

## 4. 仓库里现成能用的零件（出处已核对）

| 需求 | 现成能力 | 位置 |
|---|---|---|
| 减伤层数 | 乘算减伤，按来源键增删，幂等（重复调用只改数值） | `LivingThing#addDamageReduction(Object,double)` / `removeDamageReduction` |
| 侵蚀 | 挂在我方身上的负面 `Effect`（`setNegative(true)`），勾在攻击方或被击方皆可 | `effect/Effect.java`、`DamageEvent` |
| 苦痛缠绕 | BOSS 自己的一个 `long` 账本字段（不需要新框架能力） | 新实体内部 |
| 灾难之力 → 加伤 | 攻击增强百分比 / 全属性增伤 | `setAttackEnhancePercent`、`setEnhance` |
| 击杀者拿额外回合 | **直接 `new TurnEntry(entity, needTime, presentTime)` 加进时间轴**；构造函数自己从控制器快照 `ActionSignal.NORMAL`，**不要动 ActionSignal** | `TurnManager.getTurns().add(...)`，`needTime = 10000/速度` |
| BOSS 召唤容器 | 同阵营加敌人 | `Fight#addEnemy(LivingThing)`（范例：`InsectBossSkillSummonEnemy`：先 `new`，再按阵营 `addEnemy`/`addFighter`） |
| 多段伤害 / 按层数分段 | `Skill` 自带 `atkMagnification`，循环打 | `Counterattack#comeToEffect` 是现成的 8 段循环 |
| 目标数 3 | 技能 `aims = 3` | `Skill` 构造参数（`CommonAttack(0, 1, 0, 2)` 的最后一个参数） |
| 效果表 | `Effect`（id/level/lastTime/origin/tags）＋ `whenLastTimeEnd` | `EffectTags`：`INFINITE/NEGATIVE/POSITIVE/SKIP_ACTION/CAUSE_DAMAGE/UNIVERSAL`（后两个至今没人用） |
| 注册 | `OfficialGameContent#addEntity` / `addEffect` | `officialStuff/OfficialGameContent.java` |

### 4.1 关键缺口（要新写的）

1. **容器的死亡通知 + 击杀者**：全项目没有 `lastAttacker`。
   `makeDamage` 会 post 带 attacker 的 `DamageEvent`，但 `LivingThing#getDamage` 不记攻击方。
   → 建议容器自己订阅 `DamageEvent` 记最后一击者（**不动框架**），
   再在"容器死掉"时通知 BOSS（掉减伤层数 / 残破容器 −1 灾难之力 / 完整容器给奖励）。
2. **容器的"存活过本回合"判定**：用 `TurnEntry#addLastSpecialAction(...)`
   （白厄「最后一击」就是挂在当前回合的 `lastExecuteList` 上）。
3. **容器实体**：新写（残破容器 / 完整容器）。
4. **大招按层数分段**：新写。
5. **二阶段高额免伤**：复用减伤来源键，要定"何时开始/结束"。
6. **侵蚀的载体**：新的 `Effect` 子类，「按损失生命值的比例」这条要定义清楚。

## 5. 分步计划

### 第 1 步：可打版本（形态一）

- 新增实体 `FlameReaver`（盗火行者）＋ `BrokenContainer`（残破容器）＋ 注册；
- 灾难之力（不设上限）：层数 / 加伤 / 被残破容器击杀 −1；
- **苦痛缠绕账本**：召唤消耗自身生命 → 记账 → 吸收时按账本回血；
- **来源绑定**：只有「本次攻击召唤的、且处于共祭的」容器能被吸收 / 一同攻击；
- 减伤层数：每死 1 个残破容器 −1 层；
- 侵蚀：由【将尽的命数】挂上；
- 技能：亡死的黑云（3 目标 + 召唤）、将尽的命数（全体 + 侵蚀 + 召唤）、
  相混的道途（上共祭）、幽冥的悼念（一同攻击 + 吸收）、却是必要的苦难（大招按层数分段）。

### 第 2 步：奖励线与形态二

- **完整容器**：击杀给"击杀者额外回合 + 增伤 buff"，没击杀被吸收充能；
- 二阶段：【沉默的悲叹】蓄力 →【莫因舍弃而哭泣】；
  【迷失的共祭】/【镣锁】：消耗 1 层灾难之力复活被杀容器；
  高额免伤替代「退居幕后」。

## 6. 已知风险 / 要小心的地方

- **容器死亡判定与回合循环**：`FightTurnPastListener` 每回合开头
  `removeIf(!isAlive())` 会把死掉的容器摘掉并调 `whenFightEnds()` ——
  容器的"结算"要挂在这条路径上或更早（`DamageEvent` 里），否则会漏。
- **减伤层数是"数量驱动"**：召唤 +1、死亡 −1，容易漏路径导致减伤永久残留。
  建议每次变化都**重设**（同一来源键幂等）。
- **来源绑定别写丢**：「曾被该攻击召唤」这条要真的按次记录（给容器打一个召唤批次标记），
  否则会退化成"吸收场上所有容器"，苦痛缠绕的账本就没意义了。
- **灾难之力不设上限**：拖久了 BOSS 无限增伤。若手感不对，优先给吸收加冷却，
  而不是改成"层数只影响大招段数"。
- **回血 ≠ 充能**：官方原文里吸收同时做两件事（回血 + 得灾难之力），
  但"吸收治疗时不再额外加灾难之力"这类区分要写清楚，别合并成一个动作。
- **阶段二复活循环**：灾难之力 ≥1 就能复活镣锁容器，配合"不设上限"可能变成打不死。
  需要给复活设条件（官方是"消耗 1 层 + 一定比例生命值"，注意别让 BOSS 自己掉死）。

### 8.1 伤害标定规则（改任何倍率前必读）

**换算常数（实测得出，直接乘即可）**：

```
打白厄时，每 1.0 技能倍率 ≈ 923 点伤害
依据：亡死的黑云 4.3 倍率实测打出 3969 点 → 3969 / 4.3 = 923
```

这个常数已经把攻击力、防御系数、增伤、抗性全部吃进去了，所以**改倍率只要乘 923**，
不要再自己去套 `攻击 × 防御系数 × …` 那一串 —— 我在这一点上连续推错两次：

- 第一次按"攻击 = 1213"推，倍率算小了（落地只有 253，远低于目标的 800~1000）；
- 第二次换成"每 1.0 倍率 ≈ 230"（从另一局的日志推的，混进了暴击/减伤差异），
  又算大了约 4 倍 —— 亡死的黑云 4.3 倍率直接把满血白厄秒了（3969 > 3796）。

**标尺（用户给的，按原游戏手感）**：

| 档位 | 伤害 | 用途 |
|---|---|---|
| 普通攻击 | 200~300 | 亡死的黑云、将尽的命数 |
| 高伤害 | 600~1000 | 却是必要的苦难（大招） |
| 少量 | 100 上下 | 残破容器的共祭招式 |

当前各技能预期（打白厄、无减伤）：亡死的黑云 ≈ 277、将尽的命数 ≈ 230、
大招单段 ≈ 923、大招收尾 ≈ 1100。

> 注意 1：打**卡厄斯兰那**（变身形态，防御带 +30% 防御增强 ≈ 1071）时防御系数更低，
> 同样倍率伤害会低约 25%。
> 注意 2：容器是**每回合都出手**的（不是一次性的），所以它的招式倍率要比本体低一个数量级，
> 否则几只容器叠起来比 BOSS 本体还痛。

### 8.2 召唤批次归属（容易写错，实测踩过）

官方「分离的哀痛」限定的是"<b>曾被该攻击召唤</b>且处于【共祭】的残破容器"——
也就是**每个招式只回收它自己召唤的那批**：

- `FlameReaver` 用两个列表分开记账：`cloudOfDeathSummons` / `fateDrawsNearSummons`；
- 招式施放时 `rememberSummon(this, container)` 入账；
- 下次施放同一招式时 `drainSummonedContainers(this)` 取出并清空，交给
  `absorbSacrificedContainers(fight, 那批)` 结算（协同攻击 → 吸收）。

**写成"吸收场上所有共祭容器"是错的**：那样容器只活一轮，玩家永远看不到协同攻击，
"共祭"这个状态也失去意义（就是第一版的表现）。

**苦痛缠绕的记账单位**：召唤时把<b>实际消耗的生命值</b>记在容器身上
（`BrokenContainer#painCost`），吸收时按这笔账回血 —— 不是按容器的最大生命，
两者比例不同（召唤 3% 最大生命 / 容器生命 12% 最大生命），混用会让回血虚高 4 倍。

### 8.3 阵营方法语义（实测确认，别再靠名字猜）

```java
fight.getOpponentList(entity)   // entity 对面的实体列表   ← 取目标用这个
fight.getOwnList(entity)        // entity 自己一侧的实体列表 ← 遍历"自己的召唤物"用这个
```

自测 `testFlameReaverFactions()` 会打印诊断，实测输出：

```
enemiesList           = [至黑之剑，盗火行者, 残破容器]
fighterList           = [测试玩家]
getOpponentList(BOSS) = [测试玩家]              ← 对面
getOwnList(BOSS)      = [至黑之剑…, 残破容器]    ← 自己一侧
```

所以分工是：

- **技能取目标** → `FlameReaverSkill#fightingSideOf()` → `getOpponentList(user)`；
- **找自己的容器** → `FlameReaver#getAliveContainers()` → `getOwnList(this)` + 类型过滤。

> 我在这一处连续改错两次（把两个方法读反），最后是靠自测打印的实际名单定死的。
> **教训：方法名有歧义时，先让代码把实际数据打出来，别继续推理。**
> 这条也是 `testFlameReaverFactions()` 里那几条语义断言存在的原因。

### 8.4 死亡离场与战斗结束已拆分（框架修复，2026-09）

**症状**：残破容器打自己的 BOSS（`残破容器攻击了至黑之剑，盗火行者造成了65`）、
BOSS 被自己的【侵蚀】烧、日志里出现 `死因=KILLED isAlive=true hp=9600`。

**根因**：`FightTurnPastListener` 在生物死亡、被移出阵营列表时调的是 `whenFightEnds()`，
而 `LivingThing` 的基类实现是"整场结束时的重置"，里面有 `setHp(getHpMax())`
→ 死掉的召唤物被**满血复活**，而它已经不在任何阵营列表里
→ `Fight#getOpponentList` 落到"不在 fighterList → 返回 enemiesList"分支 → **打自己的 BOSS**。

**框架修复**（把两个语义拆成两个钩子）：

```java
LivingThing#whenLeaveFight(Fight)   // 新增：单个生物离场，只做结算+清理，绝不复位血量
LivingThing#whenFightEnds()         // 保持原义：整场结束的重置（补满血/清效果/清冷却）
```

| 调用点 | 改前 | 改后 |
|---|---|---|
| `FightTurnPastListener` 的 `theDeath` 循环 | `dead.whenFightEnds()` | `dead.whenLeaveFight(fight)` |
| `FightEndEventListener` 遍历 `getAllEntities()` | `entity.whenFightEnds()` | 不变 |

**容器侧**：离场逻辑（通知 BOSS 掉减伤层数 + 清残留）搬进
`BrokenContainer#whenLeaveFight(Fight)`；不再需要重写 `whenFightEnds()`。
官方「为我设奠」的"重新召唤"属于阶段二，要显式 `new` 一只新的实现。

> 影响面：`whenFightEnds()` 全项目只有 2 个调用点、3 个重写（Phainon / ActorLiXiaoYan / FlameReaver），
> 三个重写都只调 `super` 或做自己的战斗结束清理，**没有实体依赖"死亡时被复位"**，所以拆分是安全的。

### 8.4.2 离场结算的**时机**：必须紧跟"移出阵营列表"（2026-09 再修）

**症状**：打死【完整容器】后日志里出现 `【酒剑仙】获得了一个额外回合`，但那一回合**从没发生**，
紧接着是 `【破容器之赏】…的增伤结束了` 与战斗失败。

**根因**：拆分出 `whenLeaveFight` 时，结算被放在**回合末尾**（`theDeath` 循环原本在
`lastExecuteList` 之后）。而 `theDeath` 是在**下一圈的循环开头**才收集的，
于是"死亡 → 结算"中间隔了**一整个回合**：

```
[我方回合] 大招打死容器（HP→0，仍在阵营列表里）
[敌方回合] 循环开头才收集死者 → 敌方行动（把击杀者打死）→ 回合末尾才结算 → 发奖给已倒下的人
```

而「完整容器」的奖励是**额外回合**（`FlameReaver#grantExtraTurn`：`needTime = 0`、
`startTime = 当前时间点`），拖到那一刻才发，受益人已经倒下 → 刚排上的条目
立刻被 `TurnManager#removeTheDeath` 摘掉 = 白拿。

**修法**：把 `theDeath` 的 `whenLeaveFight` 循环从回合末尾挪到
`TurnManager.removeTheDeath()` **之后、判定胜负之前**（`FightTurnPastListener`）。

```text
循环开头：收集死者(removeIf) → removeTheDeath() → whenLeaveFight 结算 → 判定胜负 → 取下一个回合
回合末尾：只剩 lastExecuteList 与 EffectUpdateEvent
```

挪到判定胜负**之前**还有两个附带好处：镣锁容器复活会先把新敌人加进 `enemiesList`，
胜负判定看到的就是真实场面；新排的额外回合条目也能拦住"时间轴空了"的兜底 `break`。

**配套**：`FlameReaver#grantContainerReward` 增加"击杀者已倒下就不发"的判据，
避免再打印一条发不出去的"获得了一个额外回合"。

**另一处（用户 2026-09 提问后补的）**：`grantExtraTurn` 排出来的条目原本**没标 `isExtra`**，
于是 `EffectEventListener:19` 走"正常回合"分支、把受益人身上效果的 `lastTime` 也减了 1 ——
刚发的【破容器之赏】（3 回合）在"被奖励的那次行动"里就少 1 回合，【侵蚀】【宿醉】也跟着多跳一次。
已改成 `.setExtra(true)`，与白厄的额外回合同一个约定（额外回合不推进效果回合数），
自测里也加了一条断言把这个标记钉住。

> 影响面：全项目**只有 `BrokenContainer` 重写了 `whenLeaveFight`**，所以这次时序调整
> 实际只影响盗火行者的容器结算；自测（222 条）不驱动回合循环，也不受影响。

### 8.4.1 不要改 `isAlive()` 的判据（考虑过，否掉）

曾考虑把 `isAlive()` 改成"不在 `allEntities` 里就算死"，**否掉**，三处理由：

1. **时序自相矛盾**：`FightTurnPastListener` 正是用 `isAlive()` 决定要不要把实体移出
   `allEntities`（`removeIf`）——死掉的实体在被移除**之前**仍在 `allEntities` 里，
   那一刻它会被判成"活着"；
2. **会砸到未参战的实例**：注册表模板、自测里 `copy()` 出来的实例都不在 `allEntities` 里，
   `isAlive()` 会变 false；
3. **`allEntities` 会被清空**（`FightEndEventListener` 收尾时 `clear()`），清空后所有实体都成"死的"。

`isAlive()` 还带副作用（死亡时重置 `ActionSignal`），把"列表成员身份"接上去会让控制器状态跟着列表变化。

**改用了两个更安全的做法**（都已在代码里）：

- `BrokenContainer#whenLeaveFight()`：**清理照做、绝不复位血量**（框架已把死亡离场与战斗结束拆开，见 §8.4）；
- `FlameReaver#summonContainer()`：`Fight#addEnemy` 之后**显式补一次 `container.whenFightStart(fight)`**
  —— 中途召唤的实体收不到开局那次遍历，这是框架里真实存在的一个缺口（虫皇的召唤物同样收不到）。

### 8.5 【共祭】做成效果（2026-09）

**症状**：`【残破容器】的共祭状态结束了` 打印在**我方回合**，导致 BOSS 下一次行动时
已经无共祭容器可吸收。

**根因**：共祭原本是容器上的一个计数（`updateSelf()` 里减 1），但框架的
`updateSelf` 是**每个回合对全场所有实体**调用的（`FightTurnPastListener` 里的
`for (entity : getAllEntities()) entity.updateSelf()`），所以计数掉得比"自己的回合"快得多。

**修法**：共祭改成**效果** `SacrificeRite`（`officialStuff/customEffect/flameReaverEffects/`），
于是：

- **回合递减交给框架**：`EffectEventListener` 在每个回合结束时统一处理 `lastTime`
  （到期调 `whenLastTimeEnd` 并移除），不需要自己数回合；
- **带 origin**：`enterSacrifice(turns, reaver.getUUID())` —— 记的是施加者（盗火行者）的 UUID；
- **可被净化**：任何"清除负面效果"的手段都能把它摘掉，玩家多一条对抗途径；
- **注册进效果表**（`OfficialGameContent`，角色专属、不标 `UNIVERSAL`），
  这样运行时实例的 id 会被 `World#registeredIdOf`（按类查表）补成
  `game_official_content:sacrificeRite`。

配套改动：

| 位置 | 改动 |
|---|---|
| `BrokenContainer` | 删掉 `sacrifice` / `sacrificeTurns` 字段与 `updateSelf` 计数；新增静态 `hasSacrificeRite` / `findSacrificeRite` / `removeSacrificeRite`；`enterSacrifice(turns, origin)` 挂效果 |
| `FlameReaver#getSacrificedContainers` | 判定改为"身上有没有 `SacrificeRite`" |
| `FlameReaver#absorbContainer` | 吸收后用 `removeSacrificeRite` 摘掉标记 |
| `TangledPathsOfMourning` / 共祭窗口 | 用 `SacrificeRite.DEFAULT_LAST_TIME`（= 3 回合，够撑到 BOSS 下一次行动）与 `reaver.getUUID()` |

> ⚠️ 一个副作用：`SacrificeRite` 是**负面**效果，而容器的「为我祷咏」会抵抗控制类负面效果 ——
> 如果共祭被自己的抗性挡掉，把那个检查从"所有负面"收窄到真正的控制类 id 即可。
> 目前 `enterSacrifice` 走的是内部 `addSacrificeRite`（跳过检查），所以不受影响。

### 8.6 轮转不再"连着两招还用不了"（2026-09 实测反馈）

**症状**：日志里频繁出现

```
至黑之剑，盗火行者的「相混的道途」还用不了，顺延到下一招
至黑之剑，盗火行者的「幽冥的悼念」还用不了，顺延到下一招
```

**两个原因**（都不是冷却，技能都是 `coolDown = 0`，原版也没有冷却）：

1. **条件式技能在玩家清场时必然落空**，而且**顺序上有死结**：
   第 1 步【亡死的黑云】/ 第 2 步【将尽的命数】也带吸收逻辑（官方「分离的哀痛」），
   于是第 3 步刚标好的共祭容器，往往被**下一圈的第 1 步**吃掉，
   第 4 步【幽冥的悼念】永远等不到共祭容器。
2. 两招都写了"没目标就不放"的 `canUse`，落空就打印"还用不了"。

**修法**：

- **吸收只由【幽冥的悼念】负责**：`CloudOfDeath` / `FateDrawsNear` 不再调
  `absorbSacrificedContainers`（召唤批次仍然照记，便于以后恢复）；
- **【相混的道途】改成无条件施放**：场上没有容器时开一个
  {@code SACRIFICE_WINDOW_TURNS = 2} 的"共祭窗口"，窗口内**新召唤的容器直接进入共祭**
  （`FlameReaver#openSacrificeWindow` / `consumeSacrificeWindow`）；
- 【幽冥的悼念】保留前提（没有共祭容器确实无事可做），但上面两条保证它通常有活干。

**意外收获**：这也顺带说明了原版为什么"放不出来也照放"——条件式技能在轮转里
必然产生空放回合，官方把条件收进技能内部（放了没效果），而不是拒绝施放。

**另外**：`FightStartEventListener` 现在会给实体接上战斗上下文
（`setParticipateFight`，此前全项目无人赋值），技能里就能用
`user.getParticipateFight()` 判断阵营了；中途召唤的实体由召唤方补同样的初始化。

### 8.7 大招可以空放（别再改）
- 曾经加过"灾难之力 >= 1 才放"的闸门，被用户否掉：
  **官方设定里这一招就是可以空放的** —— 0 层时它只有收尾那一击。
- 玩家清召唤物换来的收益是"这一招打得轻"，**不是**"这一招被延后"。
- 同理，玩家在自己回合清光容器 → 第 3 步无人可上共祭 / 第 4 步落空，都是设计内。

> 注册的意义：`World#registeredIdOf` 按**类**查表，没注册的运行时效果 id 会停在短名。

**苦痛缠绕为什么用 `level` 存数值**：`Effect` 的 `equals/hashCode` 只看 `id` / `origin` / 是否无限，
所以改 `level` 不会让它被当成"另一种效果"而叠出第二份。

### 9.2 实测暴露的问题与修法（重要，别改回去）

1. **`forceNextSkill` 是"下一个回合"生效，不是"紧接着"** ——
   第一版想用它把吸收推后，结果中间插进玩家回合、容器被清掉，`幽冥的悼念` 永远等不到共祭容器。
   → 现在按官方顺序把「相混的道途」与「幽冥的悼念」作为**两个独立轮转步**，不靠 forceNextSkill。
2. **吸收必须限定"自己召唤的那批"**（见 §8.2），否则容器只活一轮、协同攻击看不见。
3. **`幽冥的悼念` 是独立的一步**：曾与「相混的道途」合并，被官方资料纠正后拆开。

### 9.3 设计决定（实现时定的）

1. **被吸收的容器不掉减伤层数**：官方"每有 1 个残破容器<b>被消灭</b>后失去 1 层"，
   吸收不算消灭，所以用 `DeathReason` 区分。
2. **容器死亡通知写在 `whenLeaveFight`**（框架已把"死亡离场"与"战斗结束"拆成两个钩子，见 §8.4）。
3. **血量不靠等级成长系数**：成长公式是 `(等级-1) × 系数 + 200`，
   用等级去凑血量会把攻击/防御一起放大。盗火行者与虫皇都改成构造器里显式 `setHpMax/setHp`。
4. **吸收只由【幽冥的悼念】负责**（见 §8.6）：早前 `CloudOfDeath` / `FateDrawsNear` 也吸收，
   会和第 4 步抢容器，导致那一步永远落空。

## 10. 验收方式

- `powershell -ExecutionPolicy Bypass -File .\test-command-system.ps1`：确认全量编译通过（基线 **222/0**）；
- `powershell -ExecutionPolicy Bypass -File .\check-sources.ps1`：编译前的静态自查（括号 / BOM / 缺 import /

**阶段一手测清单**（已在游戏中验证通过，日志见对话记录）：

1. BOSS 按 亡死的黑云 → 将尽的命数 → 相混的道途 → 幽冥的悼念 → 却是必要的苦难 出手；
2. 召唤出来的容器**占用回合**（下一回合轮到它）；
3. 打掉容器后 BOSS 掉 1 层减伤；
4. 上共祭后不管它，下一轮「一同攻击 + 吸收回血 + 涨灾难之力」；
5. 大招按灾难之力层数打出对应段数。

**阶段二手测清单**（已跑通，2026-09）：

1. 血量 ≤50% 时打印 `进入二阶段：获得高额免伤（70%）`，此后受到的伤害显著下降（实测 4026 → 1207 / 339）；
2. 触发 `进入【沉默的悲叹】状态，开始蓄力` → 攒 2 层灾难之力 → 召唤 2 只【镣锁】容器；
3. 下一次行动施放 `莫因舍弃而哭泣`，顺序是 **起手全体 → 按层数追加**（与阶段一相反）；
4. 击杀【完整容器】→ `【破容器之赏】… 增伤 +40%` + `获得了一个额外回合`；
5. 放着不管的完整容器被吸收 → 额外获得灾难之力；
6. 三回合后 `【破容器之赏】… 的增伤结束了`，且**不应**再出现
   `这里写效果具体内容........请重写这个方法`（那是 `comeIntoEffect` 没重写的症状，已修）。
